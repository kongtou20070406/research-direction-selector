# 招募开源贡献者与研究协作者 · RDS

[English](RECRUITING.md) · [项目首页](../README.zh-CN.md) · [贡献指南](../CONTRIBUTING.zh-CN.md)

**让 AI 更好地辅助人进行科研。** 我们欢迎愿意围绕这个目的，一起参与的开源贡献者与研究协作者。

好的科研辅助，应当帮助人澄清问题、比较解释、设计公平的实验，并理解结果能说明什么。也应保留失败路线与决定理由，让研究者能够审阅、纠正和继续这项工作。

Research Direction Selector（RDS）是我们选择的实现形式。你可以贡献科研案例、评估方法、代码、交互改进或教程。从一项自己能检查的小成果开始，不需要先掌握全部组件。

## 我们在做什么

RDS 通过本地决策与执行系统，连接研究者和 Codex、Claude Code 等 AI 助手。研究者确定问题、目标、投入与科学接受；AI 提供假说、分析和实验提案；Advisor 将声明的目标连接到证据与候选路线；内核保留执行、成本、失败和恢复。详见[愿景与范围](rds-purpose.zh-CN.md)。

我们希望改善真实科研中的 AI 辅助：比较更清楚，结论忠于证据，减少重复工作，跨会话仍能接续。这些收益需要与研究者一起评估，并有独立任务证据。含糊的建议、RDS 增加的负担，以及它帮不上忙的案例，都值得报告。

## 为什么值得参与

- **改善研究者实际需要的帮助。** 把提问、比较、解读或接续中的困难，转成一项可以评估的具体改进。
- **留下别人能复核的成果。** 一个可复现的失败、评价器、受检适配器或清楚的教程，都能成为下一位贡献者的起点。
- **同时接触科研与工程。** 问题表述、公平比较、Python 执行、事务状态与形式化检查在同一个工作流里相遇。
- **从适合自己的台阶开始。** 先改清楚一个安装步骤或整理一个小型公开案例，再考虑新算法或新适配器。

## 可以参与的方向

| 你的兴趣 | 可以先交付什么 | 从哪里开始 |
| --- | --- | --- |
| **科研工作流与科学方法** | 把自己遇到的失败整理成最小公开或合成案例：原问题、竞争解释、已观察失败与区分检验。 | [科研工作流](research-workflow.zh-CN.md)、[问题结构评估](problem-structure-evaluation.md) |
| **独立评测** | 制作有标准答案与评价器的任务；同条件比较辅助质量，记录决定质量、研究者投入和全部结果。区分纯 Agent 测试与有人参与的评估。 | [基准任务贡献指南](../CONTRIBUTING.zh-CN.md#贡献基准任务)、[基准协议](../benchmark/README.md) |
| **Advisor 与问题修订** | 复现缺失证据、前提变化或路线被否决后，下一决定应当改变的案例，改进对应的有范围行为。 | [程序持有的 Advisor](program-owned-advisor.md)、[问题结构](problem-structure.md) |
| **执行内核与恢复** | 构造小型中断或重复调用案例，检查原回执、尝试和花费，再修复确认的故障。 | [CPU 回执示例](../examples/autoresearch-receipts/README.md)、[开发反馈循环](development-loop.md) |
| **数学与领域适配** | 选一个准确命题、支持的后端和最小输入，保留真实证书、反例或 `UNKNOWN` 及其假设。 | [形式化验证](formal-verification.zh-CN.md)、[领域确认](domain-confirmation.md) |
| **人机协作与易用性** | 检查研究者能否理解建议、审阅证据并纠正它；改进含糊的工作流或安装步骤。 | [快速入门](quickstart.zh-CN.md)、[宿主插件](host-plugins.md) |
| **文档、翻译、教程与设计** | 修正一处误导声明或失效步骤，翻译指南，或制作能看到原始结果改变后续行动的教程。 | [文档导航](README.zh-CN.md)、[贡献指南](../CONTRIBUTING.zh-CN.md) |

不改内核，也可以贡献案例、解释、教程或测试报告。使用自己有权公开的材料；制作合成案例时保留与问题相关的失败行为。

## 如何开始

1. 按[两分钟上手](../README.zh-CN.md#两分钟上手)试用，再阅读自己感兴趣方向的指南。
2. 浏览[开放 Issue](https://github.com/kongtou20070406/research-direction-selector/issues)，开始前核对当前讨论、相关 PR 和作者。Issue 仍开放，不代表无人认领或已经可以编码。
3. 错别字或有准确复现的聚焦 bug，可以直接提 PR。较大功能、新 schema 或科研行为变更，先开 Issue 讨论问题、最小有用范围与检查方法。
4. 提交时说明改了什么、为什么有用、实际做了哪些验证、还有什么未确定。有用的负面结果或复现，即使暂时没有修法，也是一项贡献。

不确定从哪里开始，可以[开一个 Issue](https://github.com/kongtou20070406/research-direction-selector/issues/new/choose)，简单介绍：

```text
我想参与 RDS。
我的兴趣或技能：
我遇到过的科研或软件问题：
我可以先交付的一项小成果：
我打算怎样检查它：
```

## 一起工作的约定

欢迎借助 AI 完成贡献；贡献者仍需理解改动并检查结果。报告真实命令、环境、结果和限制。公开日志或产物前先自己检查，凭据、私有会话与研究数据留在私有记录中。

尊重已有作者与约定范围。不同意见友善表达，用证据解决技术分歧。详细实现、审查、证据与许可约定统一见[贡献指南](../CONTRIBUTING.zh-CN.md)。

## 联系方式

可以在对应 Issue、PR 讨论中交流，或使用[新建 Issue 入口](https://github.com/kongtou20070406/research-direction-selector/issues/new/choose)。说明想参与的方向，以及第一项最小有用成果。
