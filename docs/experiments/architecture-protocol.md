# 实验协议：架构 × 数据顺序 × weight decay 交叉

预注册。写于任何实验运行之前，判定规则不改。
目的有两个，第二个更重要：

1. 检验「架构 A 比架构 B 好」这个说法，在**控制训练 loss** 之后是否还成立。
2. 检验 RDS 在 DL 场景里有没有增量——同一份实验，用 RDS 记录和用朴素脚本记录，
   结论会不会不同。

第 2 个是这份协议真正的用途。如果两种记录方式得到的结论一样，RDS 在 DL 上的价值
就只剩「省事」；如果不一样，差异出现在哪里，就是它值多少钱。

---

## 1. 假设

**H0（默认，教科书版）**：某个架构的优势是架构固有的，换数据顺序、换正则化强度、
换 seed，排名不变。

**H1（可证伪）**：排名来自训练协议选择的解，不是架构本身。换协议后排名可以反转。

这条 H1 来自 `docs/dl-first-principles.md` 的 L2-A：经验风险对解欠定，训练协议选择
解。如果 L2-A 在真实任务上不成立，这份协议应该把它推翻，而不是给它背书。

---

## 2. 因子与水平

| 因子 | 水平 | 为什么选它 |
|---|---|---|
| 架构 | 4 个：`bare`（单头注意力 + 线性头）、`+residual`、`+pre-ln`、`+mlp`（注意力后加一层 MLP） | 覆盖「裸注意力」到常见块结构；每次只加一个机制 |
| 数据顺序 | 2 个：`shuffle`（每 epoch 重排）、`curriculum`（按样本难度升序，难度=训练集 loss 分位） | L2-A 的第一条推论：更新不交换 → 顺序有影响 |
| weight decay | 3 个：`0`、`1e-4`、`1e-1` | 覆盖无正则、温和、强正则；L2-A 的第二条推论 |
| seed | 5 个（任务规模允许时；至少 3） | 少于 3 个不算观察 |

总格数 4 × 2 × 3 = 24 格，每格 5 seed = 120 runs。CPU-only 下每 run 目标 ≤ 60 秒，
总量约 2 小时。如果超时，先砍 weight decay 到 2 个水平并在记录里写明。

---

## 3. 数据

**首选 Kaggle 小任务**，便于对外复现。候选（按下载成本排序）：

- `digit-recognizer`（MNIST，42k 训练）——足够大，CPU 上每 epoch 约 1-2 秒
- `zalando-research/fashionmnist`（72MB）——同量级，类别更难
- 兜底：`sklearn.datasets.load_digits`（1797×64），零下载，用来先把管线跑通

划分：固定 `dev` / `test`，用同一个 `random_state`，在协议里写死。**test 只在最后
看一次**，所有选择在 dev 上做。

输入形态（让注意力有序列结构）：把 28×28 切成 49 个 4×4 的 patch = 49 token × 16 维，
或者 16 个 7×7 patch。具体选择写进记录，不能事后改。

---

## 4. 训练协议（关键：怎么匹配 loss）

单次 run 记录**完整轨迹**：每 `k` 步记录 `train_loss`、`dev_loss`、`dev_acc`。

- **固定预算终点**：跑满预算时的 `dev_acc`。
- **匹配 loss 点**：找 `train_loss` 第一次降到目标 `L` 的那一步，记录当时的 `dev_acc`。

`L` 预注册为「所有格子里，5 seed 中位数的最终 train loss 的 75 分位」，在看到任何
`dev_acc` 之前算出来。**如果某个 run 到预算结束都没降到 `L`，记 `UNREACHED`，不进
主指标的分母**，但必须出现在报告里。

主指标是匹配 loss 点的 `dev_acc`，不是终点 `dev_acc`。理由：终点 acc 混入了「优化
难度」和「归纳偏置」两件事，L2-A 说必须分开。

---

## 5. 预注册判定规则

对每一对架构 (A, B)，在协议格 g 下计算
`delta(g) = acc_matchedloss(A, g) - acc_matchedloss(B, g)`，取 5 seed 的均值。

| 判定 | 条件 | 结论 |
|---|---|---|
| **架构固有优势成立** | 所有 g 的 `delta(g)` 同号，且 `min|delta(g)| > 2 × max_seed_std(g)` | 「A 优于 B」可保留，且写明只在测试过的协议范围内有效 |
| **排名反转** | 存在 `g1, g2` 使 `delta(g1) · delta(g2) < 0` 且两者都超过 2×标准差 | H0 被推翻。必须撤回「架构固有优势」，改写成「在协议 g 下 A 更优」 |
| **无差异** | 所有 `|delta(g)| ≤ 2 × max_seed_std(g)` | 判为「在当前预算下不可区分」，不许写「A 略优」 |
| **不可判定** | 该格 `UNREACHED` 超过 2 个 seed | 标 `UNKNOWN`，不许用剩余 seed 凑结论 |

门槛用相对比例（2× seed std），不用绝对点数。理由：绝对点数在 1797 样本的数据集上
不可迁移。

---

## 6. 记录要求（缺失即无效）

每个 run 必须记录，缺一项该 run 不进分母：

- 架构名与它相对 `bare` 的**唯一改动**（一句话）
- `seed`、数据顺序策略、weight decay
- 训练超参（lr、batch、步数、优化器）与**初始化方式**
- **模型身份**：不用模型时写 `none`；用模型时写 provider/model/version，以及 token
  用量来自哪里
- 完整轨迹（`train_loss` / `dev_loss` / `dev_acc` 采样）
- 目标 `L` 的取值与它的计算过程
- 是否 `UNREACHED`

「模型身份缺失」这一项是硬要求。RDS 现在记 token 不记身份，这条协议要求补上；在
补齐之前，任何「用了模型」的记录都算无效。

---

## 7. 两个臂

| 臂 | 怎么做 | 目的 |
|---|---|---|
| **朴素臂** | 手写脚本 + CSV 日志 | 目前的常规做法 |
| **RDS 臂** | 同一份训练代码，通过 RDS 的判定协议 + 账本 + 回执跑 | 检验增量 |

两臂用**同一份训练代码**，只换记录与判定层。这样差异只可能来自记录与判定。

比较三件事：

1. **结论是否相同**：两臂对每一对架构给出的判定（成立/反转/无差异）是否一致。
2. **能否复现**：隔一天重跑，两臂能否给出同一个判定；RDS 臂应能靠账本回放，朴素臂
   靠人记得当时做了什么。
3. **假认证**：两臂各自有没有出现过「看起来 PASS 但换个口径就翻」的情况。这一项
   用 `false_certification` 计数，定义见 `benchmark/newtonbench` 的现有实现。

第 3 项是 RDS 唯一可能的护城河：**它不是让你更快，是让你更早发现自己算错了。**

---

## 8. 预算

- CPU-only。单 run ≤ 60 秒，总预算 ≤ 3 小时。
- 探测预算：先用 1 个 seed × 4 架构 × `shuffle` × `wd=0` 跑通管线，占总预算 ≤ 10%。
  探测失败则整份协议判 `BLOCKED`，不是 `REFUTED`。
- 不加新仪器。`rank_experiments` 保持现状，不在这份协议里用。

---

## 9. 这份协议不做什么

- 不做 EIG 选点。EIG 对随机的对照现在没有区分力（两边都 2 个点就收敛），在这份协议
  里跑等于没比。
- 不碰 Compass 的语法闭合问题。那是另一件事，见下面第 11 节。
- 不追求 SOTA。主指标是「同 loss 下的泛化」，不是榜单分数。

---

## 10. 预期结果与它的意义

**如果 H1 成立（出现排名反转）**：说明「架构固有优势」这类结论在 DL 文献里普遍
不可靠，因为它没有控制协议。同时说明 RDS 的记录层有用——因为只有记录了顺序和 WD，
才有可能发现反转。

**如果 H0 成立（排名稳定）**：说明这两个架构的优势确实稳健。这时候 RDS 的增量只能
体现在复现与假认证计数上，不能声称「改善了研究结论」。

**两种结果都必须公布。** 只报 H1 成立是选择性报告，和这份协议要防的东西是同一个。

---

## 11. 与「语法闭合」问题的关系

批评报告指出的核心问题是：假说必须先 `parse` 进声明语法，实验必须先躺在调用者给的
离散点里，真定律在语法外时只会截断或误认证。

**这份协议不解决那个问题**，它是另一条线上的事。但它提供了一个干净的对照：如果连
「架构 × 顺序 × WD」这种完全在语法内的任务，RDS 都没有增量，那么去改语法闭合就是
在错误的优先级上工作。

所以顺序是：先跑这份协议，再决定要不要动 `compile_hypothesis` 那道门。

---

## 12. UNKNOWN

- 任务规模（42k MNIST）是否足以观察 L2-A 的效应，没有先验。如果 120 runs 全部
  「不可区分」，那就是预算不足，不是假设被推翻——这一点必须写进结论文本。
- CPU 上 60 秒/run 能否让 4 个架构都降到目标 `L`，未验证；探测臂就是为这个准备的。
- 两臂的「假认证计数」在 DL 任务上没有既有实现，需要新写判定代码——这属于工具，不算
  新仪器，但在协议里要单列。
